GuardDuty Detects Threat

GuardDuty continuously analyzes:

VPC Flow Logs

CloudTrail logs

DNS logs

Example detection:

Trojan:EC2/BlackholeTraffic

Meaning:

EC2 instance is communicating with known malicious IP.

GuardDuty Generates Finding (JSON)

GuardDuty creates a finding like:

{
  "type": "Trojan:EC2/BlackholeTraffic",
  "resource": {
    "instanceDetails": {
      "instanceId": "i-123456"
    }
  },
  "service": {
    "action": {
      "networkConnectionAction": {
        "remoteIpDetails": {
          "ipAddressV4": "185.x.x.x"
        }
      }


EventBridge Rule

Your rule:

{
 "source": ["aws.guardduty"],
 "detail-type": ["GuardDuty Finding"],
 "detail": {
   "type": ["Trojan:EC2/BlackholeTraffic"]
 }
}

What it does:

Filter ONLY this type of finding.

It does NOT contain IP logic.

EventBridge forwards FULL finding JSON to Lambda.

Lambda reads:

detail.resource.instanceDetails.instanceId
detail.service.action.networkConnectionAction.remoteIpDetails.ipAddressV4

So Who Knows the Malicious IP?

Answer:

GuardDuty detection engine.

AWS maintains threat intelligence lists.

GuardDuty compares traffic against:

known botnets

C2 servers

malware IPs

BlackholeTraffic” Actually Means

It usually means:

EC2 talking to known malicious destination.

Not necessarily inbound attack.

Could be:

malware installed

compromised instance

botnet communication

What Lambda Usually Does

Lambda gets:

Instance ID
Suspicious IP

Then performs actions like:

🟢 Option 1 — Modify Security Group (Most Common)

Remove internet access:

Detach SG
Attach quarantine SG
🟢 Option 2 — Add NACL Rule

Block malicious IP.

🟢 Option 3 — Stop Instance

Emergency isolation.

Explination:
==============
In our OTT application, EC2 instances were internet-facing and handled high traffic volumes. We implemented GuardDuty-based automation so that if suspicious traffic like Trojan or blackhole communication was detected, EventBridge triggered Lambda to isolate the instance automatically. This reduced incident response time and prevented potential service impact or lateral movement.

Why not Polling GuardDuty API?

Polling means lambda will run for every x minutes so incase the attack happens now and lambda will be triggering after 3-5 minutes that's too late and continuous API calls lambda invokes costly affair
